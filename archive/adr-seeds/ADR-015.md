**Context.** The harness loads instruction files by location — a root file plus per-subtree files that load on demand. That handles *where you are*. It does not handle *what kind of thing you are editing*.

**Decision.** Adopt both. Keep the native parent-child hierarchy for location-scoped context, and add rule files carrying a `paths:` glob in frontmatter for kind-scoped context — authoring conventions on all markdown, protocol rules on the orchestration tree, retrieval doctrine on the knowledge base. Every rule file opens with the failure it prevents, not with the rule.

**Consequences.** An agent's instruction set becomes a function of what it is touching, orthogonally to where it started. Both mechanisms already exist in the harness, so this is configuration.

**Failure of the simpler design.** Location-only scoping cannot express a rule that applies to every markdown file in an estate. The predecessor uses glob scoping exclusively and gets the complement wrong in the other direction — neither half alone is sufficient.
